# GitHub 与 Gitee 双源自动更新设计

## 目标

山竹漫剧每次正式发布只构建一套经过签名、公证和校验的产物，并将同一批文件发布到 GitHub 与 Gitee。客户端启动后后台检查更新，国内网络优先使用 Gitee；Gitee 不可访问或数据无效时自动切换到 GitHub。发现新版本只提示用户，由用户确认下载和安装，不静默强制升级。

## 方案选择

### 采用：一次构建，双仓发布，客户端自动容灾

- GitHub Actions 是唯一构建入口，避免两边分别构建后产生不同 Hash。
- 同一提交、标签、安装包、更新清单、完整更新包和增量补丁同步到两个公开仓库。
- 客户端默认使用“自动”更新源，先解析 Gitee 最新正式 Release，再回退 GitHub。

### 不采用：GitHub 与 Gitee 分别构建

两次构建可能产生不同签名、Hash 或补丁链，无法证明两边提供的是同一版本。

### 暂不采用：另建对象存储或更新服务器

独立 CDN 的稳定性和控制力更强，但需要新增服务器、域名和运维成本。当前双仓规模不需要该层；后续只需增加一个更新源解析器，不改客户端更新业务。

## 模块边界

### 更新源解析

服务端桌面模块负责把逻辑来源解析成 Electrobun 可读取的文件目录：

- `auto`：Gitee 优先，失败后 GitHub。
- `gitee`：仅使用 Gitee，便于诊断国内镜像。
- `github`：仅使用 GitHub。
- `custom`：保留开发者自定义目录。

Gitee 没有与 GitHub 完全等价的稳定 `latest/download` 文件目录。解析器先读取公开接口 `https://gitee.com/api/v5/repos/Chance-Ccc/mangosteen-studio/releases/latest`，仅接受正式版本和 `vX.Y.Z` 标签，再生成标签固定的目录：

`https://gitee.com/Chance-Ccc/mangosteen-studio/releases/download/vX.Y.Z`

解析出的实际目录在一次“检查 → 下载 → 安装”事务中固定使用，禁止从 Gitee 清单切换到 GitHub 下载文件。

### 客户端启动检查

- 桌面客户端完成基础启动后自动检查一次，不依赖 AIHubKit 登录状态。
- 检查在后台进行，不阻塞登录、项目加载或画布使用。
- 没有新版本时不提示；有新版本时复用现有更新入口显示版本号。
- 用户点击后下载，下载完成后再次由用户确认安装并重启。
- 开发模式和远程连接模式不自动更新。

### 发布镜像

GitHub Actions 先完成所有平台构建与产物校验，再执行两个发布目标：

1. 发布 GitHub Release。
2. 将同一提交和标签同步到 Gitee，创建同名正式 Release，并上传同一批附件。

Gitee 发布需要最小权限的 GitHub Actions Secret。Secret 只用于工作流，不写入源码、日志、安装包或客户端设置。任一镜像上传失败时发布任务失败，并明确指出失败平台；已发布文件不自动删除，修复凭据或网络后安全重跑同版本镜像步骤。

## 数据与安全校验

- 两边的 `main`、发布标签和 Release 目标提交必须一致。
- 两边附件名称、文件大小和 SHA-256 必须一致。
- 客户端沿用更新清单中的应用标识、平台、架构、版本和 Hash 校验，并阻止降级。
- Gitee 返回非正式版、非法标签、缺失清单、错误平台或网络超时时，`auto` 才回退 GitHub。
- 下载或安装阶段失败时保留当前版本，显示中文错误和手动下载入口。

## 首次启用边界

- `v0.1.1` 仍是手动更新基线；仅有 DMG，不能伪装成可自动更新版本。
- 自动更新从下一次完整发布开始，版本至少为 `v0.1.2`，且必须包含 Electrobun 更新清单和完整更新包。
- Apple Silicon macOS 自动安装需要 Developer ID 签名与 Apple 公证；未满足时只发布手动安装包，不向客户端宣告可自动更新。

## 验收标准

1. GitHub 与 Gitee 的 `main`、标签、Release 附件 Hash 一致。
2. 国内网络可从 Gitee 检查并下载新版本；Gitee 故障时可回退 GitHub。
3. 旧版客户端发现新版后只提示，不自动安装；用户确认后完成下载、安装和重启。
4. 更新后版本号和构建 Hash 与目标清单一致；失败时旧版本仍可启动。
5. 未提交文件、API Key、Gitee Token、签名证书和私钥不进入任何仓库或安装包。
